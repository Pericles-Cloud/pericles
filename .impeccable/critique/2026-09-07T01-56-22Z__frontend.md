## Design Specificity Verdict

**LLM assessment**: This is not a reskinned admin template. The token system (`globals.css`), Atlas's sea-route/vessel-tracking layer, per-subsidiary fleet coloring, and domain-specific event iconography (typhoon, earthquake, cyber, maritime) show real investment in the supply-chain domain — the shell and Atlas are bespoke and disciplined. But that investment is uneven: login/register, the workflow node palette, and most CRUD list pages (suppliers/shipments/carriers/organizations/agents) fall back to generic "card + form + fixed-modal" SaaS-admin vocabulary. Most tellingly, the brand serif (`font-display`, Cormorant) never appears on login/register — the first screen every user sees is the least "Pericles" screen in the app.

**Deterministic scan**: `impeccable detect --json frontend/src` ran clean structurally (exit 2, i.e. findings present) and returned **14 findings, all the same rule** (`border-accent-on-rounded`, "Border accent on rounded element"), spread across 12 files (`atlas/page.tsx`, `intelligence/page.tsx` ×2, `(portal)/layout.tsx`, five `manage/*` pages, `auth/callback/page.tsx` ×2, root `page.tsx`, `data-source-settings-dialog.tsx`). **All 14 are false positives** — I independently verified 3 of them and the sub-agent verified all 14: every flagged element is `animate-spin rounded-full h-8 w-8 border-b-2 ...`, the standard Tailwind loading-spinner idiom (a single-side border on a spinning circle renders as a rotating ring, not a clashing border-on-card). The detector's heuristic (rounded + thick single-side border) has no way to distinguish "spinner" from "bordered card" from static markup alone. **Net result: the deterministic scan found zero real defects.** Worth a one-line addition to `.impeccable/config` (or an inline ignore) so this rule stops firing on every spinner in the codebase — 14 identical false positives on one idiom is itself a signal the rule needs a spinner exception, not that the codebase has 14 problems.

**Visual overlays**: Not available. No browser-automation/computer-use tool is exposed in this session (confirmed via tool search by both the parent and Assessment B), so no live server, script injection, or user-visible overlay was attempted. This critique is source-code-only; there is no rendered-pixel evidence behind these findings, so anything that would only show up in the browser (actual computed contrast under `color-mix`, real layout wrapping at specific widths, animation feel) is not covered here.

## Overall Impression

The app's best moment (Atlas) sets a bar the rest of the product doesn't clear. The gut read: this team can clearly do rigorous, accessible, domain-specific design when they invest in it (the token system's contrast-ratio comments, RiskBadge's icon+label+color rule, the sidebar's focus trap) — but that rigor isn't systematized, so it shows up in some places and is completely absent in others right next to them. The single biggest opportunity is consolidation, not new design: one severity representation, one color system on Atlas, one set of shared Dialog/Select/Switch/Tabs primitives. Almost every Priority Issue below traces back to the same root cause — there is no shared component for the thing that's inconsistent.

## What's Working

1. **The design-token system's discipline.** `globals.css` documents contrast ratios inline, closes the default Tailwind color palette so off-brand hex values can't compile, and treats severity as "named by meaning, never by color alone" — `RiskBadge` enforces icon+label+color redundancy so a colorblind user or a black-and-white printout never loses the signal. That's unusually rigorous for an internal tool.
2. **Atlas's route/vessel modeling.** Real port-to-port sea routes (not straight lines), a solid/dashed split at the vessel's live position, and per-subsidiary fleet coloring with a matching legend. This is bespoke domain work, not a generic map with pins dropped on it.
3. **Honest incompleteness signaling, where it's visible.** The Assessments "Coming soon" card and the disabled Co-Pilot controls' tooltips ("Not available yet") are refreshingly honest instead of faking functionality — the *how* it's shown has issues (see cognitive-load notes), but the instinct not to pretend a feature exists is the right one.

## Priority Issues

**[P0] No confirmation on the highest-consequence action in the product, on the surface where it's used most**
- **What**: The workflow editor's "Run" button (`plans/[workflowId]/page.tsx:294-307`) fires a real workflow run — actual emails/SMS/Slack to external recipients — with zero confirmation dialog. The equivalent action from the Plans list view (`plans/page.tsx:146-152`) does confirm, with a comment explaining the list-view choice: *"This is one click deep in a ⋮ menu, so confirm before anything leaves the building. The detail page has separate Trial and Run buttons and does not need this."* That's a real, considered rationale — not an oversight — but the mitigation is one `variant="outline"` vs. default-filled button and a Zap-vs-Play icon, sitting shoulder-to-shoulder at the same size. For an action this hard to undo, that's thin cover, especially under the exact pressure (a live disruption) this product exists to help people handle calmly.
- **Why it matters**: This is the single highest-consequence, hardest-to-undo action in the app, reachable from the surface where users spend the most time. A misclick here sends real external communications; a misclick on "Trial Run" doesn't. Relying on button-variant discrimination alone for that gap is a textbook error-prevention failure regardless of how deliberate the original tradeoff was.
- **Fix**: Route both entry points through one shared confirmation component with copy matching the stakes, rather than a native `confirm()` in one place and nothing in the other. If the editor's two-button layout is kept, make Run visually costlier to hit by accident (separation, color, or a brief hold/type-to-confirm for `run` mode specifically, mirroring the "type DELETE" pattern already used elsewhere).
- **Suggested command**: `/impeccable harden`

**[P1] Three unrelated, uncoordinated color systems live on the busiest screen (Atlas)**
- **What**: On Atlas, vessel/route color encodes *subsidiary*, pin color encodes *origin vs. destination*, and event-marker color encodes *event type* via raw hex values (`#EF4444`, `#F97316`, `#F59E0B`, `#3B82F6`, `#10B981`, `#6B7280` — `atlas/page.tsx:775-782`) that bypass the risk-severity token system entirely — confirmed in the source.
- **Why it matters**: `globals.css` deliberately closes off ad hoc Tailwind colors specifically to prevent this kind of drift, and `RiskBadge` exists so severity always reads the same way. Atlas routes around both. A user has to hold three unrelated, un-labeled legends in working memory simultaneously on the one screen where they need to move fastest — a direct violation of the app's own "≤4 items in working memory" bar and its own stated color discipline.
- **Fix**: Fold event-type into the existing risk-severity family where the two concepts overlap (most event types already imply a severity), or clearly separate them as two named, always-visible legends instead of one implicit color language competing with itself. Route markers through the same tokens `RiskBadge` uses rather than a local hex map.
- **Suggested command**: `/impeccable colorize`

**[P1] Severity — the single most important number in a risk platform — is rendered three incompatible ways**
- **What**: `RiskBadge` (word + icon + color, e.g. "Critical" with an octagon-alert icon) vs. a bare colored numeral disc in `SEVERITY_CONFIG` (`intelligence-utils.ts:66-70`, used by `event-list.tsx:74-77` — literally renders "1"/"2"/"3" with no label) vs. Atlas's type-keyed hex dots (above). Confirmed by reading all three call sites directly.
- **Why it matters**: This directly undermines "recognition rather than recall" — a returning user has to re-learn what "3" means on the Intelligence feed after learning "Critical + octagon icon" means the same thing on the Dashboard, and neither matches what a colored dot means on Atlas.
- **Fix**: Retire the numeric-disc variant; render `RiskBadge` (or its icon+label convention) everywhere severity is shown, full stop.
- **Suggested command**: `/impeccable distill`

**[P1] Notification toggles in personal Settings are fully wired to look live and are not**
- **What**: `settings/page.tsx:223-261` — "Email Notifications," "Weekly Digest," and "Push Notifications" are `role="switch"` elements with `aria-checked` hardcoded to a static `"true"`/`"false"` string and **no `onClick` handler at all**. Confirmed by reading the block directly — there is genuinely no state or handler wired to any of the three.
- **Why it matters**: Unlike the disabled Co-Pilot buttons elsewhere (visibly dimmed, tooltip-explained), these render as fully interactive, styled switches. A user who toggles "Weekly Digest" off believes they've changed a real preference; nothing happened, and it will silently appear "on" again next visit. Worse, `aria-checked="true"` asserts a false state directly to a screen reader — that's an accessibility defect, not just an unfinished feature, on a screen most people won't revisit to notice something's wrong.
- **Fix**: Either wire these to real preference state now, or apply the same visible "coming soon" disabled treatment used for the Co-Pilot controls so the UI never asserts a state it doesn't back up.
- **Suggested command**: `/impeccable harden`

**[P2] No shared Dialog / Select / Switch / Tabs primitives**
- **What**: `frontend/src/components/ui/` has button, card, dropdown-menu, fillet, input, label, and risk-badge — no Dialog, Select, Switch, or Tabs. Every modal across Plans/Suppliers/Carriers/Organizations/Agents hand-rolls `fixed inset-0 bg-black/50`; every toggle hand-rolls its own translate-x switch (including the two dead ones above); tabs are implemented independently at least twice (Intelligence's Feed/Analytics switch, Settings' 5-tab strip).
- **Why it matters**: This is the mechanical reason the inconsistencies above exist and keep recurring — there's no single component to fix once and have the fix propagate. Every new modal, toggle, or tab strip is a fresh chance to reintroduce the same class of gap.
- **Fix**: Extract Dialog, Select, Switch, and Tabs into `ui/` (Radix is already a dependency via dropdown-menu/label), migrate call sites, and the confirmation/toggle-state fixes above become one change instead of five.
- **Suggested command**: `/impeccable harden`

## Persona Red Flags

**Alex (Impatient Power User)** — primary action: triage a new critical event fast, then trigger a response.
- No header-level indicator of new critical events anywhere (`components/layout/header.tsx` has no bell/badge) — Alex has to proactively open Dashboard or Intelligence to learn something happened, the opposite of what a monitoring tool's power user wants.
- On the Intelligence feed, Alex has to remember that a red circle with "3" in it means the same as the "Critical" `RiskBadge` seen three clicks earlier on the Dashboard.
- Lands exactly on the Trial-Run/Run pair (`plans/[workflowId]/page.tsx:277-307`) that the P0 above calls out — a fast, confident click is precisely the failure mode a missing confirmation exists to catch.

**Sam (Accessibility-Dependent User)** — primary action: navigate and parse severity/status via screen reader or keyboard alone.
- Atlas's event markers are plain map `Marker`/`Symbol` circles colored by raw hex with no accessible label or text alternative (`atlas/page.tsx:775-798`) — a screen-reader user gets nothing from the event layer beyond the separate Events Feed list.
- The dead notification toggles are especially bad for Sam: `aria-checked="true"` is asserted to assistive tech with no way to ever change it — a false accessibility signal, not just a visual one.
- Counter-example worth naming: the theme picker in `settings/page.tsx` and the sidebar's modal focus trap show the team clearly *can* do rigorous ARIA/keyboard work — the gap is inconsistency, not inability.

**Riley (Deliberate Stress Tester)** — primary action: probe destructive/high-stakes flows under pressure.
- Finds the Run-with-no-confirmation gap (P0) immediately.
- Finds "Leave Organization" (`manage/organizations/page.tsx:525`, confirmed: `onClick={handleLeaveOrg}` with no confirmation anywhere in the handler) fires with zero confirmation, immediately next to "Delete Organization," which does gate behind a confirm step.
- Finds that deleting a workflow from the Plans grid uses a native browser `confirm()` (`plans/page.tsx:303`) while every other destructive action in the app (delete account, delete organization) uses an in-app "type DELETE" card — a jarring, unbranded interruption the first time you hit it.

## Minor Observations

- Login/register use `font-bold` for their headings while the rest of the app uses the brand serif (`font-display`) — the one font that says "Pericles" never appears on the first screen a user sees.
- Two separate routes both render an on-page heading of "Settings" (`/settings` and `/manage/settings`) with no on-page label distinguishing them; only the sidebar disambiguates ("Org Settings"), so a bookmark or back-navigation gives no cue which one you landed on.
- Dashboard's "Risk Score" blends a 60/40 max/avg client-side with the formula explained nowhere in the UI — a number risk managers will likely be asked to justify to others.
- `manage/agents/page.tsx` uses a raw `<table>` while every other manage page is card-based — worth confirming this is a deliberate fit for tabular data rather than drift.
- "Assessments" is a fully live-looking sidebar nav item leading to a "Coming soon" page, with no visual distinction (badge, dimmed state) in the sidebar itself to set expectations before the click.

## Questions to Consider

1. What if severity had exactly one visual representation in the entire codebase, and `RiskBadge` were the only legal way to render it — would the numeric-disc and Atlas-hex-color paths survive a refactor, or are they evidence the token system's rules are enforced only in `globals.css`'s comments?
2. What if the header carried one small "N critical events" indicator visible from every surface — would that change how fast Alex's real workflow (detect → triage → respond) moves more than anything else currently on the roadmap?
3. What if every "coming soon" control in the app (Co-Pilot buttons, notification toggles, Assessments) used one consistent visual treatment, so a user could tell "this is real" from "this is a preview" without reading a tooltip?
